SECTION 2 • SLIDES 07–10 + PRACTICE PDF pp. 07–12
PERSONA = WHO WE DESIGN FOR
SLIDE 07 • PDF p.07 — DEFINITION

What is a Persona? PERSONA = A RESEARCH-BASED USER REPRESENTATION

A simple, fictional profile representing an important user pattern, based on real research evidence.

✗ NOT a random imaginary person. ✗ NOT every user.
SLIDE 08 • PDF p.08 — EXAMPLE PERSONA CARD Hospital App Case
M

Maya, 34

Busy working parent • Uses her phone on the bus

GOAL Book an appointment in under five minutes.
PAIN POINT Finding available appointment times is difficult.
NEED Clear steps, readable text, and visible dates.
SLIDE 09 • PDF p.09 — THE IDEA

Build a Strong Persona: 5 Ingredients

  1. Who are they? (relevant background and context)
  2. What are they trying to do? (goal)
  3. What makes the task difficult? (pain point)
  4. How do they behave? (habits and environment)
  5. What must the interface support? (need)
Every ingredient must trace back to research data!
SLIDE 10 • PDF p.10 — DIAGNOSTIC COMPARISON “A persona helps us make choices.”
✗ WEAK PERSONA

“Ali, 25. Likes technology and coffee.”

→ This does not tell us how to design. (Irrelevant trivia with zero task or interface implications).

✓ USEFUL PERSONA

“Ali books appointments on a small phone screen. He needs to see the next free time quickly.”

→ Now we know what to improve. (Specifies device constraint + actionable UI priority).

SECTION 3 • SLIDES 11–13 + PRACTICE PDF pp. 13–17
SCENARIO = WHEN + WHAT (CONTEXT STORY)
SLIDE 11 • PDF p.13 — DEFINITION & FORMULA

What is a Scenario? SCENARIO = A SHORT STORY

It describes a person trying to achieve a goal in a real situation. Focus on human context, not low-level UI widgets.

1. WHO
(Actor/Persona)
2. WHERE / WHEN
(Real Context)
3. GOAL
(Why Needed)
4. ACTION
(What They Do)
5. DIFFICULTY
(Obstacle/Time Limit)
SLIDE 12 • PDF p.14 — EXAMPLE SCENARIO

Maya Books a Visit

“Maya is on the bus to work. Her child needs a doctor visit. She opens the hospital app, checks free times, and books a pediatric appointment. She wants to finish before her bus stop.”
Discuss: Why does the bus context change our design?
Because she is on a moving bus with divided attention, one hand holding a strap, small mobile screen glare, and a strict time deadline before her stop—requiring large targets, minimal typing, and immediate slot visibility.
SLIDE 13 • PDF p.15 — KEY DISTINCTION

Persona vs. Scenario

PERSONA = WHO
  • Maya
  • Working parent
  • Uses a mobile phone
  • Needs short, clear steps
SCENARIO = WHEN + WHAT
  • On a bus before work
  • Needs pediatric care
  • Looks for free times
  • Books an appointment
★ Rule: Same persona → many possible scenarios.

“Between two lectures, Deniz needs a quiet room for four teammates. On a phone, Deniz opens the university library portal and searches for rooms available at 15:00. SECTION 4 • SLIDES 14–15 + PRACTICE PDF pp. 18–21
USE CASE = USER + SYSTEM INTERACTION
SLIDE 14 • PDF p.18 — DEFINITION

What is a Use Case?

USE CASE = USER + SYSTEM INTERACTION. A structured description of how an actor reaches a goal using a system.

01 • Actor Patient (Maya)
02 • Trigger Needs appointment
03 • Main success Appointment confirmed
Emphasize: Use cases describe interactions, not screen layouts.
SLIDE 15 • PDF p.19 — HOSPITAL APP USE CASE

Use Case: Book an Appointment (Actor ↔ System Dialogue)

Step 1 (User): User opens the app
Step 2 (System): System displays clinic choices
Step 3 (User): User selects Pediatrics
Step 4 (System): System shows available slots
Step 5 (User): User chooses a slot
Step 6 (System): System confirms booking
🔀 Alternative Flow: No slots? → Show other dates or clinics.
PRACTICE (8 MIN) & REVEAL SAMPLE ANSWER • PDF pp. 20–21 Main + Alternate + Error Flows
USE CASE: Reserve a library study room • Actor: Student (Deniz) • Precondition: Signed in to the portal • Success: Booking confirmation issued
1. MAIN SUCCESS FLOW (6 STEPS)
  1. Student requests rooms
  2. System lists availability
  3. Student selects slot
  4. System checks slot
  5. Student confirms
  6. System saves booking and displays code.
2. ALTERNATE PATH (ROOM FULL)

At step 4, system says unavailable → shows alternatives → user selects another slot → return to step 4.

3. ERROR PATH (CONNECTION LOST)

At step 6, show safe retry/status; do not create a duplicate booking.

SLIDE 20 & SLIDE 21 • PDF pp. 28–29 — WHAT IS A USER JOURNEY MAP?

A timeline (Before → During → After) showing the user's actions, thoughts, feelings, and difficulties from start to finish. Look for moments of confusion and opportunities to improve.

SLIDE 21 • PDF p.29 — MAYA’S APPOINTMENT JOURNEY MAP Pain Point → Design Opportunity
Row 1. Search 2. Select 3. Book 4. After booking
Action Opens app Checks clinic Chooses slot Reads SMS
Feeling Hopeful Unsure Relieved Confident
Pain point Too many menus Clinic names unclear Slow loading None
Opportunity Clear shortcut Explain clinics Show progress Easy reschedule

SLIDE 22 • PDF p.32 — REQUIREMENTS CHAIN

How Insights Become Requirements

1. Research insight: People cannot find the next available date.
2. User requirement: Users need to view available dates quickly.
3. Design requirement: Show next available appointments on the first results screen.
4. Evaluation question: Can users find a free time without help?
SLIDES 23 & 24 • PDF pp. 33–34 — FROM PAIN TO DESIGN

Practice Together: Identify the Problem

“I missed my appointment because I could not find where to cancel or reschedule.”
01 • Pain point Cancel / reschedule option is difficult to find.
02 • Need Manage existing bookings without searching.
03 • Design Add a visible “My Appointments” button.
04 • Test Ask a participant to reschedule a booking.

SLIDE 32 • PDF p.42 — EXAM TRAP ALERT

Common Mistakes to Avoid

Persona Inventing facts without evidence
Scenario Writing a feature list instead of a story
Use case Forgetting the system response or alternate path
HTA Listing screens, not user tasks
Journey Listing only clicks, ignoring emotions and problems
