★ Core Midterm Ammo
1. Shneiderman's 8 Golden Rules Week 5
Rule #1: Strive for Consistency Identical button shapes, colors, terminology, and layout patterns across all steps.
Rule #3: Offer Informative Feedback Immediate visual/auditory acknowledgment (<100ms) for every keypress or button touch.
Rule #6: Permit Easy Reversal (Undo) Relieves anxiety and encourages exploration; users must be able to step back without data loss.
Rule #8: Reduce Short-Term Memory Load Never force users to memorize codes across screens; externalize data directly on screen.
2. Norman's Principles & Triad Weeks 2 & 5
Affordance vs. Signifier Affordance = what is possible (touch screen). Signifier = where and how to act (raised 3D borders, drop shadows, explicit icons).
Feedback & Gulf of Evaluation The system must immediately reflect state change so users know their action succeeded.
Norman's Triad of Models Design Model → System Image → User Model. The user only ever sees the System Image!
Mapping & Constraints Natural spatial relationship between controls and real-world effects; physical & semantic constraints prevent slips.
3. Nielsen's 10 Heuristics Week 5
H#1: Visibility of System Status Clear progress indicators (Step 2 of 3), loading spinners, and selected states.
H#5: Error Prevention Better to prevent errors via format masks and disabled states than write great error messages.
H#6: Recognition Rather Than Recall Make options, items, and instructions visible. Do not force users to retrieve codes from memory.
H#9: Error Diagnosis & Recovery Error messages must be in plain human language, state the exact cause, and constructively offer a fix.
4. Gestalt Principles Week 2
Proximity (Closeness = Relation) Items positioned close together are perceived as functionally related; keep labels near their inputs.
Similarity (Style = Function) Items sharing visual traits (color, size, elevation) are perceived to perform the same action.
Common Region (Cards & Borders) Enclosing related fields inside a distinct container or card overrides mere whitespace proximity.
5. Mathematical Laws Weeks 2 & 3
Fitts's Law: Movement Time T = a + b · log₂(2D / W). Rapid targets are large and close. Minimum touch target = 9–10mm (48×48dp). Screen edges act as infinite width.
Hick-Hyman Law: Decision Time RT = a + b · log₂(n + 1). Decision time scales logarithmically with choices. Categorize 28 flat choices into 4 grouped categories.
Cowan's Memory Law: 4 ± 1 Chunks Working memory holds only 3–5 items for 20–30 seconds. Multi-field forms must externalize data.
6. Physiological Constraints Weeks 1–3
2° Foveal vs. Peripheral Vision Sharp reading is restricted to a 2° circle (thumbnail at arm's length). Periphery detects only motion and flicker; quiet corner text is completely ignored (inattentional blindness).
Time Constants of Usability 0.1s = instantaneous causality; 1.0s = flow intact; 10.0s = cognitive abandonment.
Gorilla Arm & Standing Posture Vertical touchscreen interactions cause arm fatigue within 60–90 seconds. Keep kiosk workflows under 3 steps.

QUESTION 1 (20 POINTS) Human Constraints & Hard Pain Points

Identify the core human constraints (perceptual, cognitive, motor, environmental) violated by this terminal and state the system's hard pain points.

1. Cognitive / Memory Constraints: Demanding an 8-character mixed alphanumeric code entirely from memory violates Cowan's 4±1 working memory chunks. Travelers under stress experience severe memory degradation.

2. Perceptual Constraints: Fluorescent lighting glare creates specular reflections that wash out low-contrast UI. Flashing 'ERR-402' in the top-left corner fails because human vision has only a 2° foveal focus; users look at the center input field and suffer from inattentional blindness.

3. Recognition Failure: Displaying 28 technical IATA codes (AMS, CDG, FRA) forces deep domain recall instead of recognition of city names (Amsterdam, Paris, Frankfurt).

⚠️ Hard Pain Points: Catastrophic error penalty (clearing fields back to blank after 2 seconds), zero error recovery, and panic caused by irreversible luggage tag printing.

QUESTION 2 (20 POINTS) Shneiderman's 8 Golden Rules (Cite 2–3 Rules)

Apply Shneiderman's 8 Golden Rules to this terminal. Cite and explain 2–3 specific rules that are violated.

Rule #6: Permit Easy Reversal of Actions (Catastrophic Violation): There is no Back or Cancel button. Once a flight button is tapped, clicking 'SUBMIT' commits permanent irreversible action (printing physical tags). Shneiderman dictates that reversible actions relieve user anxiety and foster exploration.

Rule #3: Offer Informative Feedback: The terminal provides zero selection feedback (no button depression or highlight when an airport code is touched), and error feedback is an obscure technical code ('ERR-402') that disappears in 2 seconds without explaining what went wrong.

Rule #8: Reduce Short-Term Memory Load: The terminal requires remembering booking codes from personal papers, decoding 28 cryptic airport abbreviations, and remembering what was selected with no final summary review step.

QUESTION 3 (20 POINTS) Norman's Design Principles & Triad

Analyze the terminal using Norman's Design Principles (Affordances, Signifiers, Feedback, and the Gulfs of Execution/Evaluation).

1. Missing Signifiers: The touchscreen has the physical affordance of being touchable, but starting with an "unmarked screen" lacks any perceivable signifier (e.g. animated hand prompt, "Touch Anywhere to Begin" button) telling novice passengers how to initiate interaction.

2. Massive Gulf of Execution: The user does not know what format the system expects for the booking reference (case-sensitive? hyphens?), bridging the gulf of execution with blind guesswork.

3. Massive Gulf of Evaluation: When the terminal flashes 'ERR-402' in the periphery for 2 seconds and wipes the screen, the user has no way to evaluate what happened: Did the system crash? Was the flight cancelled? Was the code mistyped?

4. Broken Norman Triad: The designer's mental model assumed a tech-savvy frequent flyer who knows IATA codes; the resulting System Image is cryptic, completely shattering the ordinary passenger's User Model.

QUESTION 4 (20 POINTS) Nielsen Usability Heuristics & Empirical Laws

Evaluate this interface against Nielsen's Usability Heuristics, Hick's Law, and Fitts's Law.

1. Nielsen H#1 (Visibility of System Status): No progress tracker (Step 1 of 3), no breadcrumb, and no selected flight confirmation before printing.

2. Nielsen H#9 (Help Users Recognize, Diagnose & Recover from Errors): 'ERR-402' uses internal system jargon instead of plain human language ('Booking reference not found. Please re-check your 6-digit code or scan your passport'). Wiping the screen destroys any chance of recovery.

3. Hick-Hyman Law ($RT = a + b \log_2(n + 1)$): Presenting 28 flat unsorted airport codes dramatically inflates decision reaction time, causing queue bottlenecks in the departure hall.

4. Fitts's Law ($T = a + b \log_2(2D / W)$): The critical 'SUBMIT' button is "small" ($W$ is narrow), dramatically increasing movement time and finger mis-tap error rates.

QUESTION 5 (20 POINTS) Component-Level Improvement Recommendations

Provide concrete architectural improvement recommendations for 4 specific components of this scenario system.

Component Current Failure Architectural Redesign Recommendation
1. Identification Component Forced manual typing of 8 alphanumeric characters from memory. Add a multimodal optical barcode & passport scanner below screen (Curb-cut effect). Keep on-screen touch keyboard as fallback with auto-formatted chunked boxes (XXX - XXX).
2. Flight Selection Component 28 cryptic IATA codes in flat unsorted grid. Group flights by departure time or region (Hick's Law). Display full city names (London Heathrow - LHR) with airline logo (Recognition over Recall).
3. Review & Confirmation Component Instant irreversible printing with no back button. Insert a dedicated Summary Review Screen (Step 3 of 3) showing passenger name, flight number, baggage count, and a prominent BACK TO EDIT button (Shneiderman Rule #6: Undo).
4. Error Management Component Tiny grey 'ERR-402' in corner + 2s screen wipe. Center inline error banner with red border and icon. Express in plain language: "Booking code not found. Please check ticket or press Call Staff." Never wipe entered text (Nielsen H#9).

Q1 • 5 PTS

Human-Centered Design (HCD)

Linked: Week 1 (S03–04) • Week 6.1 (S02–07)

Prompt: “Is this interface appropriate for its target users? Consider at least two user needs.”

(a) Observed UI Elements (Screen 1, 2, 3): Screen 1 displays language selection (“TR EN AR”) as tiny, borderless plain text in the top-right header, while Screens 2 and 3 lack any language selection buttons. Users are forced to manually enter “Patient ID” on both Screen 1 and Screen 2. For error recovery, Screen 1 only provides a faint grey footer notice: “If your operation fails, try again or visit the counter.”
(b) HCI Reasoning (2 Core Target User Needs Violated): Human-Centered Design requires adapting technology to the physical, cognitive, and contextual limits of real users (older adults, first-time visitors, low digital literacy, stressed patients):
  • Need 1 — Visual & Language Accessibility: Older adults with age-related presbyopia and reduced contrast sensitivity struggle to read tiny, low-contrast grey instructions across Screens 1–3, and non-native speakers cannot switch languages once past Screen 1.
  • Need 2 — Low-Friction Task Flow & Guided Support: Forcing stressed patients to type a hospital ID twice without an alternative ID Card / Barcode Scanner or a visible “Call Staff” help button makes the system machine-centered rather than patient-centered.
(c) Likely User Impact & What Must Be Tested: Impact: Seniors and first-time visitors will likely abandon the kiosk and crowd the reception counter. Usability Testing Need: Because static mockups cannot show physical ergonomics or live error recovery, we must test with older adults and first-time visitors to measure task completion rates, standing-posture readability, and error recovery when a Patient ID is forgotten or unrecognized.
Q2 • 5 PTS

Visual Perception & Attention

Linked: Week 2 (S06–25) • Week 3 (S57–69)

Prompt: “What elements attract attention? Is important information easy to notice and read?”

(a) Observed UI Elements: The dark blue header banner (“CITY GENERAL HOSPITAL”) and bold black section headings (“WELCOME / CHECK-IN”) dominate visual attention. Conversely, critical operational warnings—“* required” (Screen 1), “Fields marked * are mandatory. All fields *” and “Why needed?” (Screen 2), and “No changes can be made later.” (Screen 3)—are rendered in tiny, low-contrast light-grey text on an off-white background. Furthermore, all buttons (Appointment, Other, NEXT, CONFIRM, EXIT) share the same muted grey-blue fill.
(b) HCI Reasoning (Pre-Attentive Processing, Contrast & Foveal/Peripheral Vision): Effective visual hierarchy relies on figure-ground segregation and pre-attentive cues (color contrast, luminance, size, and spatial isolation) to guide the user's 2° foveal vision. Styling all buttons in uniform desaturated grey-blue denies primary actions (NEXT, CONFIRM) pre-attentive pop. Placing the irreversible constraint “No changes can be made later.” in low-luminance grey in the bottom-right periphery guarantees inattentional blindness when the user's gaze is fixated on the summary box or CONFIRM button.
(c) Likely User Impact & What Must Be Tested: Impact: Hurried users scanning the screen will miss mandatory field rules and lock-in warnings, causing submission errors or premature irreversible confirmation. Usability Testing Need: Conduct legibility and eye-tracking tests under simulated hospital lobby lighting (including overhead glare) to verify whether users fixate on and comprehend the warning messages.
Q3 • 5 PTS

Memory & Cognitive Load

Linked: Week 1 (S08) • Week 2 (S32–43) • Week 5 (H#6, R#8)

Prompt: “Does the kiosk favor recognition over recall? What may increase mental effort?”

(a) Observed UI Elements: Screen 1 demands “Patient ID: (* required)”. Upon advancing to Screen 2, the form asks the user to type “Patient ID” a second time alongside Full name, Date of birth (DD/MM/YYYY), and Mobile phone. Additionally, Screen 2 displays “STEP 2 / 3” but shows zero reminder of which service was selected on Screen 1.
(b) HCI Reasoning (Recognition Rather Than Recall & Working Memory 4±1 Limit): This interface violates Recognition over Recall and overloads fragile working memory (capacity ~4±1 chunks for 20–30 seconds). Instead of letting users recognize their appointment via a barcode scan or National ID lookup, it forces them to retrieve an arbitrary hospital Patient ID from long-term memory. Re-entering Patient ID on both Screen 1 and Screen 2 imposes redundant cognitive and motor load, hiding the selected service violates externalized state (Shneiderman Rule #8), and overlapping labels on Screen 1 (Reports vs. Lab results, Information vs. FAQ vs. Help?) force extra mental interpretation.
(c) Likely User Impact & What Must Be Tested: Impact: High memory burden increases patient anxiety, slows down check-in, and causes data-entry mistakes. Usability Testing Need: Test whether real patients actually know their hospital Patient ID unaided, and verify whether data typed on Screen 1 auto-populates on Screen 2 (and remains preserved if the user taps CHANGE DETAILS on Screen 3).
Q4 • 5 PTS

Fitts’s Law

Linked: Week 3 (S17–23) • Week 6.1 (S04)

Prompt: “Evaluate the size, spacing, and placement of touch targets for typical kiosk users.”

(a) Observed UI Elements: On Screen 1, the language options “TR EN AR” in the top-right header are tiny, unbordered text labels packed tightly together. The “GO” button is much smaller than the 12 service buttons. Across Screens 1–3, primary navigation buttons sit at opposite extreme corners: on Screen 1, “NEXT” is at the bottom-left and “BACK” is at the bottom-right, whereas on Screens 2 and 3, “SUBMIT” and “CONFIRM” jump to the bottom-right.
(b) HCI Reasoning (Fitts's Law: T = a + b · log₂(2D / W) & 9–10mm Touch Baseline): By Fitts’s Law, movement time T = a + b · log₂(2D / W) increases with target distance (D) and decreases with target width (W). The labels TR EN AR and Why needed? have a tiny width (W) and near-zero spacing, creating a high Index of Difficulty (ID = log₂(2D / W)) and violating the 9–10 mm minimum touch target baseline (Fat Finger problem). Flipping forward navigation from bottom-left (NEXT on Screen 1) to bottom-right (SUBMIT / CONFIRM on Screens 2–3) forces a large hand travel distance (D) across a wide kiosk screen.

Q5 • 5 PTS

Hick’s Law

Linked: Week 2 (Satisficing) • Week 4 (S28) • Week 5 (H#8)

Prompt: “How might the number and organization of choices affect decision-making?”

(a) Observed UI Elements: Screen 1 presents 12 identically sized service buttons in a flat 4×3 grid (Appointment, Register, Insurance, Payments, Lab results, Doctor, Reports, Other, Change / Cancel, Information, FAQ, Help?), followed by two competing action buttons (“GO” and “NEXT”).
(b) HCI Reasoning (Hick's Law: RT = a + b · log₂(n + 1) & Overlapping Categories): According to Hick’s Law, reaction/decision time rises logarithmically with the number of choices (RT = a + b · log₂(n + 1)), and degrades into slow linear scanning when choices are ungrouped and semantically ambiguous. Here, patients must disambiguate overlapping pairs (“Appointment” vs. “Doctor”, “Lab results” vs. “Reports”, “Information” vs. “FAQ” vs. “Help?”) and then face a secondary decision bottleneck between pressing GO or NEXT.
HICK'S LAW: 12 FLAT vs. 4 GROUPED CHOICES
(c) Likely User Impact & What Must Be Tested: Impact: Causes choice paralysis, long dwell times on Screen 1, and wrong category clicks by urgent patients. Usability Testing Need: Measure time-to-first-click and category selection accuracy across realistic patient scenarios (e.g., checking in for an appointment vs. picking up a lab report).
Q6 • 5 PTS

Gestalt Principles

Linked: Week 2 (S12–16)

Prompt: “Are related functions grouped using proximity, similarity, and clear visual hierarchy?”

(a) Observed UI Elements: On Screen 1, all 12 buttons share identical size, color, border, and grid spacing even though they mix clinical tasks (Appointment, Lab results), administrative/financial tasks (Insurance, Payments), and general support (FAQ, Help?). On Screen 3, “CHANGE DETAILS”, “CONFIRM”, and “EXIT” use the same rounded grey rectangle styling, while the warning “No changes can be made later.” sits isolated at the bottom-right corner far away from CONFIRM.
(b) HCI Reasoning (Similarity, Proximity & Common Region): The interface misuses Similarity (making unrelated service categories and destructive vs. primary actions look identical) and violates Proximity and Common Region:
  • On Screen 1, lack of Common Region makes it unclear whether the Patient ID field belongs to the 12 service buttons above it or operates as a separate lookup via GO.
  • On Screen 3, separating the warning “No changes can be made later.” from the CONFIRM button violates Proximity, so users do not associate the lock-in consequence with clicking CONFIRM.
(c) Likely User Impact & What Must Be Tested: Impact: Weak visual grouping increases motor slips (e.g., accidentally tapping EXIT when intending to tap CHANGE DETAILS on Screen 3). Usability Testing Need: Conduct card-sorting studies with patients to validate service groupings and eye-tracking to confirm visual hierarchy.
Q7 • 5 PTS

Affordances & Signifiers

Linked: Week 1 (S10) • Week 4 (S29) • Week 5 (S05–07)

Prompt: “Can users tell what is clickable, editable, or required? Give concrete examples.”

(a) Observed UI Elements: On Screen 1, “TR EN AR” and “Terms, Privacy, Consent, Registration Policy, Hospital Rules” lack button borders, icons, color contrast, or underlines; the Patient ID box contains an ambiguous partial line “________”. On Screen 2, “Why needed?” is plain grey text, and the note states “Fields marked * are mandatory. All fields *”—yet none of the 4 field labels (“Full name”, “Date of birth”, “Patient ID”, “Mobile phone”) have an asterisk (*). Only Date of birth has a format hint (DD/MM/YYYY).
(b) HCI Reasoning (Norman's Affordances vs. Signifiers): While a glass touchscreen physically affords tapping anywhere, users depend on perceivable signifiers (borders, 3D shadows, high-contrast labels, underlines, asterisks, input masks) to know where and how to act:
  • Missing Clickability Signifiers: TR EN AR, Why needed?, and the policy names look like static text rather than interactive links/buttons.
  • Contradictory Mandatory & Format Signifiers: Screen 2 tells users to look for * on mandatory fields while omitting * from every label, and Patient ID / Mobile phone lack format or digit-length signifiers.
(c) Likely User Impact & What Must Be Tested: Impact: Users will not discover that they can switch languages or tap Why needed?, and will make formatting mistakes on ID/phone inputs. Usability Testing Need: Test whether users perceive TR EN AR and Why needed? as tappable, and verify whether tapping an input box displays a clear focus border and pops up an on-screen keyboard.
Q8 • 5 PTS

Feedback & Visibility

Linked: Week 3 (S03–04, S83–88) • Week 5 (H#1, R#3–4)

Prompt: “What feedback and state indicators should appear when moving between Screens 1–3, submitting invalid data, or completing check-in? What cannot be observed?”

(a) Observed UI Elements: Screen 1 lacks a step indicator, whereas Screens 2 and 3 display “STEP 2 / 3” and “STEP 3 / 3”. None of the 12 service buttons on Screen 1 show an active/selected state. Screen 2 notes “A verification code may be sent to your phone.” Screen 3 states “After confirmation, please proceed to the assigned counter.”, yet the summary box (Patient: A. SAMPLE, Appointment: Internal Medicine, Date: 14/10/2026, Time: 09:30) omits the counter or room number.
(b) HCI Reasoning (Visibility of System Status & Dialog Closure): Visibility of System Status (Nielsen Heuristic #1) requires continuous state feedback:
  • Selection & Progress State: Tapping a service on Screen 1 must highlight the button with a checkmark ([✓ SELECTED]), and Screen 1's header must show STEP 1 / 3.
  • Actionable Error Feedback: Submitting invalid data on Screen 1 or 2 requires inline red field highlighting and plain-language instructions—the static footer “If your operation fails, try again or visit the counter” violates Heuristic #9.
  • Dialog Closure (Shneiderman Rule #4): Screen 3 must display the exact assigned counter number, clinic room number, and queue number.
(c) What Cannot Be Observed in Static Images & Must Be Tested: Cannot be observed statically: Immediate button press acknowledgment (<100 ms), loading spinners during database lookup (>1 s), inline validation error messages, whether an SMS OTP verification step interrupts the transition from Screen 2 to Screen 3, and what final confirmation screen or printed ticket appears after tapping CONFIRM. All of these require interactive prototype usability testing.
Q9 • 5 PTS

Interaction Styles

Linked: Week 3 (S09–17, S31, S47) • Week 4 (S05–06, S20)

Prompt: “Is touch interaction appropriate across this three-screen journey? Discuss one advantage and one limitation.”

(a) Observed UI Elements: The three-screen journey combines Direct Manipulation / Menu Selection (tapping service buttons on Screen 1 and CHANGE DETAILS / CONFIRM on Screen 3) with intensive Form Fill-In across five text boxes (Patient ID on Screen 1; Full name, Date of birth, Patient ID, and Mobile phone on Screen 2), with no visible on-screen keyboard on either screen.
(b) HCI Reasoning (One Advantage vs. One Limitation of Touch Interaction):
  • Advantage (Screens 1 & 3 — Menu Selection): Direct touch requires zero intermediary devices (no mouse/physical keyboard to lose or vandalize) and provides immediate 1:1 hand-eye coordination for walk-up-and-use button selection and confirmation.
  • Limitation (Screen 2 — Heavy Alphanumeric Form Fill-In): Typing 5 fields of names, dates with slashes (DD/MM/YYYY), and ID numbers on a vertical glass screen suffers from the loss of tactile key edges/resistance (high slip rate), screen occlusion (an on-screen keyboard covers ~40% of the display), and Gorilla Arm muscle fatigue while standing.
(c) Likely User Impact & What Must Be Tested: Impact: Slow, error-prone typing on Screen 2 creates long lobby queues and user frustration. Usability Testing Need: Test virtual keyboard ergonomics on the physical kiosk—specifically verifying whether the system automatically switches between a large numeric keypad (for ID, Date of birth, Mobile phone) and a QWERTY keyboard (for Full name).
Q10 • 5 PTS

Multimodal Interaction

Linked: Week 3 (S51–82, S91–92) • Week 4 (S07–10, S20–22)

Prompt: “Would speech, audio cues, or other modalities help? Specify a user need and a potential drawback.”

(a) Observed UI Elements: The entire journey across Screens 1–3 relies 100% on visual reading and manual touch typing. There are zero icons or instructions for audio output, headphone jack support, voice input, barcode/ID card scanning, or physical ticket printing.
(b) HCI Reasoning (User Needs Served by Multimodal Channels): Adding complementary modalities addresses critical hospital user needs:
  • Optical Barcode / QR & National ID Card Scanner (Screens 1–2): Allows elderly or hurried patients to scan their National ID card or appointment slip instead of recalling and typing 4 personal fields.
  • Auditory Click Confirmation + Private Headphone Text-to-Speech (TTS): Helps visually impaired or low-literacy patients confirm button presses and hear instructions.
  • Physical Printed Queue Slip (Screen 3): Provides a tangible paper reminder of the clinic room, counter, and appointment time.
(c) Potential Drawback & Field Testing Need: Major Drawback (Privacy & Noise): Using open-air speech recognition or loud speaker output in a public hospital lobby breaches medical privacy/confidentiality (broadcasting patient names, IDs, and Internal Medicine appointments to strangers) and suffers high recognition error rates due to ambient lobby noise. Usability Testing Need: Conduct field testing in a real hospital lobby to evaluate barcode scanner reliability and acoustic privacy.

⚖️ TRADE-OFF 1 • PROGRESSIVE DISCLOSURE vs. INTERACTION DEPTH

Fewer Initial Choices vs. One Extra Sub-Step Tap

Collapsing 12 flat buttons into 4 macro-categories (Progressive Disclosure) drastically reduces initial choice paralysis on Screen 1 under Hick’s Law. However, the trade-off is increased interaction depth: a user who wants a specific secondary sub-action (e.g., choosing specifically between “Pay bills” vs. “Change / Cancel”) must now perform one additional sub-selection tap on the next screen instead of tapping it directly on Screen 1.

⚖️ TRADE-OFF 2 • SELF-CONTAINED INPUT vs. VISUAL SCREEN DENSITY

Always-Visible Keypad & Scanner vs. Higher Screen Density

Displaying both the Scan ID / Barcode instructions and the embedded 0–9 numeric keypad directly on Screen 1 eliminates hidden affordances and popup surprises. However, the trade-off is higher visual density on Screen 1, leaving less whitespace than a multi-page wizard that splits service selection and identification onto separate screens.

Q1. Human-Centered Design Missing language switch on later screens, tiny grey text, no help/staff button, forced manual ID entry. HCD (ISO 9241-210): Match physical/cognitive limits (presbyopia, tremors, stress, low tech literacy). Task completion rate with seniors/novices & standing-posture readability.
Q2. Visual Perception Low-contrast grey warnings in periphery, identical button colors for primary vs. secondary/exit actions. 2° Foveal vs. Peripheral Vision, Pre-Attentive Pop, Figure-Ground, Inattentional Blindness. Eye-tracking fixation on warnings & legibility under ambient lobby glare.
Q3. Memory & Load Asking for the same ID twice across screens, unmemorizable codes, missing summary of prior step choice. Recognition Rather Than Recall (H#6), Working Memory (4±1 chunks), Externalized State (R#8). Whether users know their ID unaided & whether fields auto-populate across steps.
Q4. Fitts’s Law Tiny packed links (TR EN AR), small buttons (GO), primary button flipping from left (S1) to right (S2/S3). T = a + b · log₂(2D / W), 9–10 mm minimum touch target, Fat Finger problem. Physical target size in mm on real hardware, mis-tap error rate, movement time.
Q5. Hick’s Law Large flat grid of ungrouped options (12 buttons), overlapping labels (Doctor vs Appointment), GO vs NEXT. RT = a + b · log₂(n + 1); uncategorized options force slow linear scanning & choice paralysis. Time-to-first-click & category selection accuracy across task scenarios.
Q6. Gestalt Principles Unrelated buttons styled identically; warning text placed far away from the CONFIRM button it modifies. Proximity, Similarity, Common Region (distance dictates relationship; shared style implies same role). Card sorting with users for category grouping & slip rate between EXIT / CHANGE.
Q7. Affordances & Signifiers Borderless clickable text, missing underlines, note saying “fields marked *” when labels have no *, missing input masks. Affordance (possible action) vs. Signifier (perceivable visual cue: border, shadow, *, format mask). Whether users discover unbordered links & whether tapping inputs shows focus + keyboard.
Q8. Feedback & Visibility Missing STEP 1/3, no selected button highlight, vague static error footer, missing room/counter # on summary. Visibility of System Status (H#1), 0.1s / 1.0s / 10.0s time constants, Dialog Closure (R#4). Dynamic button press state (<100ms), inline validation errors, SMS OTP flow, post-confirm screen.
Q9. Interaction Styles Touch buttons (Screens 1 & 3) vs. multi-field text entry (Screen 2) with no visible virtual keyboard. Direct Manipulation (fast menu selection) vs. Form Fill-In on Soft Keyboard (no tactile edges, 40% occlusion, Gorilla Arm). Typing speed/errors on vertical kiosk & auto-switching between Numeric Keypad vs. QWERTY.
Q10. Multimodal 100% visual/manual-typing interface; no barcode/ID scanner, audio jack, or ticket printer. Multimodal Redundancy & Curb-Cut Effect vs. Public Voice UI Privacy Breach & Ambient Noise Failure. Field-testing barcode scanner accuracy and acoustic privacy in a noisy lobby.
